# Profiling-Guided Performance Optimization of Ramulator 2.0

**Course project:** CS598APE · University of Illinois Urbana-Champaign · Fall 2026  
**Author:** Xianyang Qiu  
**Project branch:** [`optimization-v6`](https://github.com/QiuTheodore/ramulator2/tree/optimization-v6)  
**Upstream project:** [CMU-SAFARI/ramulator2](https://github.com/CMU-SAFARI/ramulator2)

## Overview

Ramulator 2.0 is a modular, cycle-accurate DRAM simulator. This project investigates **ways to reduce host-side simulation runtime and peak memory usage without intentionally changing the modeled memory-system behavior**.

The work starts from a historical Ramulator 2.0 source revision and applies a series of profiling-guided optimizations. The final selected implementation is **V6_CLEANUP** (V5_ALL plus the pending-request map cleanup). It is maintained on the `optimization-v6` branch of this fork; it is not an update to upstream `main`.

## Key optimizations

| Area | Approach |
| --- | --- |
| FRFCFS scheduling | Avoid redundant readiness checks while selecting requests. |
| DDR4 command queries | Reduce overhead in prerequisite-command and readiness evaluation. |
| DDR4 timing updates | Reduce unnecessary state updates across unrelated nodes when processing commands. |
| Last-level cache (LLC) | Reuse list nodes for LRU updates and use more direct cache-set indexing. |
| Address translation | Reuse translations for repeated access to the same recent page, when valid. |
| SimpleO3 frontend (V6) | Remove completed address entries from `m_receive_requests` rather than retaining empty lists indefinitely. |

These optimizations were evaluated in combinations in the V1–V6 development process. **The speculative instruction-window indexing variant (`V6_WINDOW`) was not selected**, because it did not produce a reliable benefit in the measured workloads.

## Experimental method

- Compared three independent **Release** builds: the original baseline, `V5_ALL`, and `V6_CLEANUP`.
- Verified that each executable loaded its corresponding `libramulator.so`.
- Checked **identical complete simulation output** across ten synthetic workloads and configurations, including different rank presets, a two-core case, and mixed read/write workloads.
- Used **12 alternating measurements per version per workload**, reporting median elapsed wall-clock time and peak resident set size (RSS).
- The longer workloads were synthetic memory-access traces, not recordings of SPEC CPU or PARSEC applications.

### Runtime results

Lower is better. Values below are medians of the final 12-run experiment.

| Workload | Original | V5_ALL | V6_CLEANUP | V6 vs. original (runtime reduction) | Speedup |
| --- | ---: | ---: | ---: | ---: | ---: |
| Unique Memory Long | 4.835 s | 3.145 s | **2.830 s** | **41.5%** | **1.708×** |
| Mixed Memory Long | 0.685 s | 0.480 s | **0.425 s** | **38.0%** | **1.612×** |
| Write Mix Long | 1.670 s | 1.180 s | **1.030 s** | **38.3%** | **1.621×** |

### Peak resident memory

| Workload | Original | V6_CLEANUP | RSS reduction |
| --- | ---: | ---: | ---: |
| Unique Memory Long | 131.0 MB | **35.0 MB** | **73.3%** |
| Mixed Memory Long | 34.3 MB | **21.4 MB** | **37.7%** |
| Write Mix Long | 48.6 MB | **16.7 MB** | **65.6%** |

The largest memory reduction is associated with cleaning up completed request entries in the SimpleO3 frontend. The exact effect depends on the workload's address reuse pattern and number of distinct pending requests.

## Correctness and limitations

**All ten selected tests produced identical simulation output** for the original, V5_ALL, and V6_CLEANUP implementations. Additionally, separate randomized differential tests were used during development to check individual algorithm transformations.

These results **do not prove equivalence for every DRAM standard, configuration, or input trace**. The benchmarks are synthetic, measurements have host/OS variability, and further evaluation on representative application traces would strengthen the findings. The results above are empirical measurements for the stated environment and workloads, not universal performance guarantees.

## Results and reproduction notes

The following measured artifacts are committed in [`performance_results/`](performance_results/):

- [`summary.csv`](performance_results/summary.csv): aggregated per-workload measurements.
- [`timings.csv`](performance_results/timings.csv): individual benchmark timings.
- [`report_summary.md`](performance_results/report_summary.md): report-ready results generated by the comparison script.

The comparison used the original baseline and separately built V5_ALL and V6_CLEANUP directories together with synthetic trace/configuration inputs from the development machine. **Those complete test inputs and build directories are not all included in this branch**, so the CSV results alone are not a turnkey reproduction package. The upstream project's README contains the general Ramulator build and usage instructions; reproducing these exact measurements additionally requires the matching historical baseline, the comparison script, and the experiment inputs.
